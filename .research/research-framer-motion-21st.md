# Research: Motion (framer-motion) & 21st.dev — fit for tilchi.uz

Research date: **Aug 1, 2026**. Verified against primary sources only — npm registry API (`registry.npmjs.org`), official docs (motion.dev, 21st.dev, gsap.com), and GitHub source (motiondivision/motion, 21st-dev/*). Bundle sizes below were **measured locally** from the published npm tarballs (`gsap@3.15.0`, `motion@12.43.0`) bundled with esbuild (tree-shaken, minified, gzip), not copied from secondary write-ups.

Versions verified on registry `latest` dist-tag, 2026-08-01: **framer-motion 12.43.0**, **motion 12.43.0**, **gsap 3.15.0**.

---

## Q1 — framer-motion vs "motion" today: same library, which to install, license

- **Same library, same version, same repo.** Both `framer-motion@12.43.0` and `motion@12.43.0` are published from the same source (`git+https://github.com/motiondivision/motion.git`) by the same maintainer (Matt Perry / popmotion), and both resolve to the identical version number. ([npm registry: framer-motion](https://registry.npmjs.org/framer-motion/latest), [npm registry: motion](https://registry.npmjs.org/motion/latest))
- **`motion` is the current name; `framer-motion` is the legacy name kept as a compatibility package.** The official repo README states it directly: *"Framer Motion is now Motion. Import from `motion/react` instead of `framer-motion`."* ([GitHub README](https://github.com/motiondivision/motion#readme)) The official docs describe Motion as "previously Framer Motion" ([motion.dev quick start](https://motion.dev/docs/react-quick-start)).
- **Installation for a new React project: `npm install motion`**, import via `import { motion } from "motion/react"` ([installation guide](https://motion.dev/docs/react-installation)). `framer-motion` still works and is more downloaded, but `motion` is the canonical, forward-looking name.
- **License: MIT on both.** Registry metadata: `"license": "MIT"` for both packages ([framer-motion registry](https://registry.npmjs.org/framer-motion/latest), [motion registry](https://registry.npmjs.org/motion/latest)); repo LICENSE.md + README: "Motion is MIT licensed" ([repo](https://github.com/motiondivision/motion#-license)).
- **Package relationship:** `motion` depends on `framer-motion ^12.43.0` (which in turn depends on `motion-dom` + `motion-utils`), so installing `motion` pulls `framer-motion` transitively — they share one codebase and version train. ([motion registry dependencies](https://registry.npmjs.org/motion/latest))
- **Downloads (npm API, last week Jul 25–31 2026):** `framer-motion` ≈ **41.1M** weekly; `motion` ≈ **17.0M** weekly. ([downloads: framer-motion](https://api.npmjs.org/downloads/point/last-week/framer-motion), [downloads: motion](https://api.npmjs.org/downloads/point/last-week/motion))
- **Caveat for GSAP comparison:** Motion's *SplitText* component is a **paid Motion+ API**, not part of the free MIT core ([feature table](https://motion.dev/docs/gsap-vs-motion)); Motion+ is a one-time payment of **£299 GBP** ([motion.dev/plus structured data](https://motion.dev/plus)). GSAP's SplitText, by contrast, ships in the free package.

## Q2 — React 19 + Next.js 16 + fully static export (SSG)

- **Peer dependencies support React 19 explicitly:** both packages declare `react: ^18.0.0 || ^19.0.0` and `react-dom: ^18.0.0 || ^19.0.0` (both optional via `peerDependenciesMeta`); `@emotion/is-prop-valid` is the only other peer, also optional. ([framer-motion registry](https://registry.npmjs.org/framer-motion/latest), [motion registry](https://registry.npmjs.org/motion/latest)) Docs: "Motion is only compatible with React versions 18.2 and higher" ([installation guide](https://motion.dev/docs/react-installation)).
- **Next.js officially supported — both Page and App Router.** For the App Router you either add `"use client"` to the importing file, **or** import from the special entry `import * as motion from "motion/react-client"`, which the docs describe as reducing "the amount of JS delivered to the client" — i.e. a RSC/SSG-friendly entry that avoids shipping the full client runtime eagerly. ([installation guide, "Next.js" section](https://motion.dev/docs/react-installation))
- **Static export works because motion is client-only.** The engine "runs animations natively in the browser using the Web Animations API and ScrollTimeline" with a JS fallback ([quick start](https://motion.dev/docs/react-quick-start)); there is no server runtime, no server-only API, and `sideEffects: false` in package.json (tree-shakable ESM) ([framer-motion registry](https://registry.npmjs.org/framer-motion/latest)). Flagged as *inferred, not an explicit doc statement*: I found no official sentence saying "works with `output: 'export'`" — but the App Router path is identical code under static export (everything pre-renders to HTML; animation hooks run only after hydration).
- **Known hydration caveats:** disable first-paint animations with `initial={false}` to avoid hydration mismatch ([quick start](https://motion.dev/docs/react-quick-start)); `AnimatePresence` exit animations require a client component. Nothing here conflicts with `output: 'export'` on Next.js 16.2.12.

## Q3 — Bundle size reality (measured) vs GSAP, and lazy-loading

**Measured locally, 2026-08-01** (esbuild bundle, `--minify`, gzip, `react` externalized — i.e. marginal cost in an app that already ships React):

| Bundle | gzip |
| --- | --- |
| `motion/react` (motion + AnimatePresence + useScroll) | **45.4 kB** |
| `motion/react-client` (same imports) | **43.1 kB** |
| GSAP core + ScrollTrigger + ScrollSmoother + SplitText + Physics2D (tilchi's current stack) | **53.7 kB** |

- **Library's own published size caps** (the `bundlesize` field in `framer-motion@12.43.0` package.json, min+gzip CI budgets): `motion` 34.9 kB, `m` 6 kB, `dom-animation` 17.85 kB, `dom-max` 29.8 kB, `animate` 19.1 kB, `scroll` 5.2 kB, `waapi-animate` 2.26 kB ([registry metadata](https://registry.npmjs.org/framer-motion/latest)). My measured 45.4 kB is higher because it includes `AnimatePresence` + `useScroll` and esbuild's tree-shaking; the 34.9 kB cap is a minimal-usage rollup.
- **GSAP individual files (measured from `gsap-3.15.0.tgz`, gzip):** core 28.4 kB; ScrollTrigger 18.0 kB; ScrollSmoother 5.5 kB; SplitText 3.7 kB. Official comparison table quotes GSAP core at 23.5 kB vs `animate()` mini 2.6 kB / full 18 kB, React API +15 kB, scroll trigger +0.5 kB (motion) vs +12 kB (GSAP) ([motion.dev: GSAP vs Motion](https://motion.dev/docs/gsap-vs-motion)).
- **Verdict: comparable footprint.** Full motion/react (~35–45 kB) is roughly equal to, or smaller than, tilchi's existing GSAP stack (53.7 kB for 5 files). Motion is not dramatically lighter in this usage.
- **Lazy-loading: yes, same pattern as tilchi's GSAP dynamic import.** The `m` component + `<LazyMotion features={...}>` loads features on demand: `m` alone is ~4.6 kB initial, `domAnimation` +15 kB, `domMax` +25 kB, and features can be fetched via a dynamic `import()` (exactly the dynamic-import-in-client-component pattern tilchi already uses for GSAP) ([reduce-bundle-size guide](https://motion.dev/docs/react-reduce-bundle-size), [LazyMotion docs](https://motion.dev/docs/react-lazy-motion)). Measured check: `m` + `LazyMotion` + `domMax` synchronous = 43.3 kB gzip — i.e. you only save by lazy-loading `domMax` via dynamic import, not by switching to `m` alone.
- **GSAP license note:** GSAP is *not* MIT — npm metadata: `"Standard 'no charge' license"` ([gsap registry](https://registry.npmjs.org/gsap/latest)); it's closed-source and owned by Webflow, with a clause prohibiting use in Webflow-competitive tools ([motion.dev GSAP comparison](https://motion.dev/docs/gsap-vs-motion)). Not a practical issue for tilchi, but relevant if licensing ever matters.

## Q4 — What is 21st.dev, and the "Magic" CLI

- **What it is:** a community registry/catalog of **12,000+ React components, templates, and shadcn themes** (2,000+ marketing blocks, 2,100+ UI components), built by named design engineers (Aceternity UI, Magic UI, shadcn/ui, Origin UI…). You browse, preview live, and copy an **AI-ready prompt** that an agent (Cursor, Claude Code, v0, Lovable) rebuilds inside your repo; every component *also* has a shadcn CLI install command. ([21st.dev homepage + FAQ](https://21st.dev/))
- **How code lands:** "the code is copied into your repo rather than imported. You own it" — no runtime dependency on 21st after install ([FAQ](https://21st.dev/)). Installs happen via (a) AI agent pasting the prompt's source, or (b) `shadcn` CLI registry install ([FAQ, "How do I install a component?"](https://21st.dev/)).
- **Stack requirements: Tailwind + shadcn/ui conventions — not optional in practice.** Components are "React + Tailwind, shadcn/ui conventions", published in the shadcn registry format and built to compose with shadcn/ui primitives and design tokens ([homepage](https://21st.dev/), [FAQ "Do components work with shadcn/ui?"](https://21st.dev/)). Framework-wise they target React (Next.js App Router is the dominant context), but the hard dependency is Tailwind + shadcn conventions — components are commonly written against `clsx`/`tailwind-merge` and often bundle `motion`/framer-motion, `lucide-react`, etc. The homepage's own example imports `cn from "@/lib/utils"` and Tailwind class strings.
- **Pricing (verified on [21st.dev/pricing](https://21st.dev/pricing), 2026-08-01):** browsing is **free** and gives **2 free component copies per day**. Paid: **Builder $6/mo** (billed yearly; unlimited copies/installs, MCP + CLI access), **Builder + AI $15/mo** (adds 500–2,000 monthly AI credits, +100 credits for $5), **Team $7.50/seat/mo** (yearly; centralized billing, shared collections, admin). Template unlocks sold as credits: 3 for $15, 5 for $22, 10 for $39.
- **The "Magic" CLI:** `github.com/21st-dev/magic` does **not exist** (404, verified). The tooling is the npm package **`@21st-dev/magic`** — an MCP server that let agents search/generate/publish components ("like v0, but in your editor"). It has been **superseded by the unified "21st MCP"**: `npx @21st-dev/cli@latest init --client cursor|claude|vscode|windsurf|codex` configures it; `@21st-dev/magic` still publishes as a thin compatibility proxy (v0.2.0+), and **all legacy Magic API keys were reset** — you need a fresh key from [21st.dev/mcp](https://21st.dev/mcp) ([magic-mcp README](https://github.com/21st-dev/magic-mcp), [cli README](https://github.com/21st-dev/cli)). The MCP server source is open (magic-mcp repo, ~5.6k stars) but the *service* requires the 21st.dev account/API key; the separate `21st-dev/cli` and `21st-dev/registry` repos are the open-source surface (MIT/Apache-2.0).

## Recommendation for Tilchi

**Motion: do not replace GSAP; only consider it for specific gaps, and only lazily.**
- The features tilchi already pays for in GSAP (ScrollSmoother page-smoothing, SplitText, Physics2D particles) have **no free equivalents in motion** — motion's SplitText is a £299 Motion+ feature, and there is no page-smoothing or 2D-physics equivalent at all ([feature table](https://motion.dev/docs/gsap-vs-motion)). Migrating would *lose* capability or cost money.
- Bundle-wise the trade is neutral-to-negative: motion/react costs ~35–45 kB gzip (measured 45.4 kB with AnimatePresence+useScroll; official cap 34.9 kB) vs the current 53.7 kB GSAP stack. Within tilchi's 280 KB total-JS CI gate either fits, but adding both libraries doubles animation payload; motion's own docs concede the `motion` component "can't be tree-shaken below 34 kb" ([reduce-bundle-size](https://motion.dev/docs/react-reduce-bundle-size)).
- If motion is ever adopted (e.g. declarative `whileInView`/`layout`/`AnimatePresence` micro-interactions GSAP does awkwardly), use `m` + `LazyMotion` with a **dynamic `import()` of features in a client component** — the identical lazy pattern tilchi already uses for GSAP — and keep it off article pages per the existing no-animation-JS gate. React 19 peer support (`^18 || ^19`) and client-only architecture make it safe on the static-export pipeline.

**21st.dev: usable as an inspiration source, not as a component supplier as-is.**
- Components assume **Tailwind + shadcn/ui conventions**; tilchi has neither (plain `globals.css`). Since code lands in-repo as source, manual porting into tilchi's CSS is *possible*, but the class-string/Tailwind token dependencies make every component a rewrite — high effort for the 2-free-copies/day free tier.
- The 280 KB gate would survive one-off ported components (their typical motion/lucide payload is ~35–45 kB), but the real cost is design-system divergence: 21st components ship shadcn tokens and styling conventions that don't exist in tilchi.
- Practical use: browse the catalog + copy prompts for **visual direction** (hero layouts, number tickers, magnetic CTAs), implement with the existing GSAP + globals.css stack. Skip the Magic MCP/CLI integration entirely — it requires a 21st API key and exists to drop Tailwind/shadcn-based source into the project, which is precisely the mismatch.

**Bottom line:** keep GSAP as the single animation runtime; treat motion as a known-compatible, MIT-licensed option for future React-declarative needs (lazy-loaded, ~35–45 kB); treat 21st.dev as a design reference only until/unless the project adopts Tailwind + shadcn/ui.
