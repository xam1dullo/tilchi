## Problem Statement

English learners and teachers in Uzbekistan need a single place to run small-group (and 1:1) live lessons, homework tests, and light classroom tools without Zoom accounts or a separate billing product. The legacy stack (`app.tilchi.uz` Presenter + CF Workers apps) mixed marketing, auth shortcuts, and live tools in ways that failed security review (webhook IP bypass, Bearer in storage, ungated deploy). Parents and payment were half-promised and not delivered cleanly.

Owners need a **greenfield rewrite**: Telegram-native login, same-origin cookie sessions, Docker/VPS runtime, LiveKit in-house meetings, optional slide/canvas, public course catalog into the bot, and a clear path to notifications and AI helper — without shipping payment or parent roles in v1, and without cutting public DNS until SEO/deploy gates pass.

## Solution

Ship **one pnpm monorepo** on an Uzbekistan VPS: nginx fronts TanStack Start (web), NestJS (API/auth/bot/canvas WS), Postgres, Redis, LiveKit, and coturn. Learners self-register in Telegram; teachers/admins are allowlisted. Core loop is **Group → Lesson → LiveKit Meeting**. Course is a public catalog that CTAs into the bot. Slide and canvas optionally attach to a Lesson. Tests use a shared bank (choice / multi / speaking). AI is a lesson helper chat only. Notifications go to web and bot. Recording, payment, parent role, and multi-language catalog stay out of v1.

Phase 1 scaffold + auth harden + Docker harden + classroom demo already landed on `main` (@ `cbb30a2`) — demo-grade: state lives in memory and the web login is not wired yet (see *Code reality*). Remaining grilled product work ships as sequential PRs (S-01 landing → slide/canvas → catalog → tests → AI → notifications → hardening), each owned by one CloudAgent writer. Public `tilchi.uz` cutover stays **HOLD**.

## Goals & Success Metrics

**v1 goals**
1. Run small-group and 1:1 lessons end to end on Tilchi's own stack — Group → Lesson → LiveKit Meeting — with no Zoom.
2. One identity: a Telegram deep link or the Mini App gives the same safe cookie session on web and in Telegram.
3. Homework that checks English: a shared test bank with choice, multi-choice and speaking answers, graded by the teacher.
4. Keep the funnel: a tilchi.uz visitor reaches bot registration and `/app` with no staff work, and no lead is lost at cutover.
5. Replace legacy app.tilchi.uz with no security regression (must-not-repeat list) and within Uzbekistan data rules.

**Success metrics (Proposed — the owner sets final targets).** Computed from Tilchi's own Postgres tables and LiveKit webhooks. No third-party analytics in v1, so learner data stays in Uzbekistan.

| KPI | Definition | Proposed target |
|---|---|---|
| Registration completion | Users who finish every bot registration field ÷ users who press Start | ≥ 70% |
| Activation | Registered learners who open `/app` within 24 h | ≥ 60% |
| Lesson attendance | Learners who join the Meeting ÷ Group learners, per Lesson that went `live` | ≥ 85% |
| Meeting reliability | Joins where LiveKit reports `participant_joined` ≤ 10 s after Nest issued the token, with no leave-and-rejoin of the same Lesson within 2 min (counted as a drop) | ≥ 98% |
| Test submission | Assignments submitted by the deadline ÷ assignments issued | ≥ 70% |
| Grading turnaround | Median time from `submitted` to `graded` | ≤ 48 h |
| 4-week retention | Learners who attend ≥ 1 Lesson in each of 4 consecutive weeks | ≥ 60% |
| Security guardrail | Sessions minted without bot confirmation or valid Mini App proof | 0 |

## User Stories

### Identity & access

1. As a **learner**, I want to register in the Telegram bot (name, level, study history, phone, goal/start), so that I can open `/app` without waiting for admin approval.
2. As a **learner**, I want Telegram deep-link confirm to mint a web session, so that I never type a password.
3. As a **learner**, I want Telegram Mini App `initData` to create the **same** `__Host-tilchi_sid` session as deep-link login, so that mobile and desktop feel one product.
4. As a **learner**, I want `/app` immediately after bot registration even with no Group, so that I see an empty state plus a Course catalog CTA instead of a dead end.
5. As a **teacher**, I want allowlist-only bot access (no email login), so that only approved telegram_ids become teachers.
6. As an **admin**, I want allowlist-only bot access with admin role, so that I can manage Groups and Course without a separate `/admin` site.
7. As a **user**, I want multiple devices signed in at once, so that phone and laptop both work.
8. As a **user**, I want web logout to clear only the current session, so that other devices stay signed in.
9. As a **user**, I want a bot **revoke-all** command, so that I can kill every session if a device is lost.
10. As a **security-conscious operator**, I want `/auth/start` rate-limited (5/min per IP, 3/min per telegram-related key), so that handoff spam is bounded.
11. As a **user**, I want pending handoffs to expire in 5 minutes, so that abandoned links die.
12. As a **user**, I want sessions to slide for 30 days, so that I am not constantly re-authing.
13. As an **attacker**, I must **not** be able to mint a session without Telegram confirmation proof (XAM-776), so that deep-link phishing cannot silently create cookies.
14. As a **future harden**, I want a short match-code in browser + bot (XAM-789), so that deep-link phishing is harder still.

### Groups & courses

15. As an **admin or teacher**, I want to create a Group, so that I can schedule Lessons for a cohort.
16. As an **admin**, I want to add learners to a Group (teachers cannot), so that enrollment stays controlled.
17. As a **teacher**, I want Groups I teach listed in `/app`, so that I can open today’s Lessons.
18. As a **learner**, I want my Groups listed in `/app`, so that I see upcoming Lessons.

22. As a **product**, I want 1:1 lessons modeled as a Group with one learner (no Booking entity), so that Meeting/Lesson APIs stay one shape.
23. As an **operator**, I want Group max 12 learners, so that room and VPS sizing stay honest.
24. As an **admin**, I want soft-delete for User, Group, and Course, so that history is recoverable without hard wipe.

### Lessons & LiveKit meetings

25. As a **teacher**, I want to create a Lesson on a Group with a scheduled Asia/Tashkent time, so that learners know when to join.
26. As a **teacher**, I want Lesson statuses `scheduled → live → ended` plus `cancelled`, so that UI and notifications stay consistent.
27. As a **teacher**, I want to press **Start** to open the LiveKit meeting (not auto-open), so that I control when video begins.

## Key Journeys & Acceptance Criteria

Each journey lists testable acceptance criteria (AC). **Now** = state on `main@cbb30a2` (Codex audit, 2026-10-28).

**J1 — Visitor to learner** (stories 1, 4, 19, 20, 58; cutover G2)
1. Visitor taps a Course CTA on tilchi.uz → `t.me/tilchiuz_bot?start=<payload>`.
2. Bot shows the privacy notice and consent button, then asks: name, English level, study history, phone (Telegram "share contact" button **(Proposed)**), goal and start date.
3. Bot confirms and offers "Open Tilchi" (Mini App or `/app`); the admin chat gets one message per completed registration.
- AC1: The bot routes `/start` by payload syntax: a handoff-shaped payload stays a login request even when expired (the user sees "expired"); a supported Course/segment payload such as `ielts_orta` prefills registration; a bare or unknown payload starts plain registration. **Now:** bare `/start` is ignored and `ielts_orta` is read as a handoff id — fails.
- AC2: Registration uses at most six data-entry prompts (consent and the final confirmation are extra); a resumed registration keeps answered fields and asks the next unanswered prompt.
- AC3: A registered learner with no Group sees the uz/ru/en empty state with "Kurslarni ko‘rish" and a Telegram CTA. **Now:** the catalog CTA leads to the home page.

**J2 — Web login by deep link** (stories 2, 10–13)
1. `/app` → "Telegram orqali kirish" → `POST /auth/start` returns a handoff and a deep link and sets a browser-binding cookie.
2. The user taps Confirm in the bot; the browser polls `POST /auth/confirm`.
- AC1: Only the Telegram user who tapped Confirm, within 5 min, in the browser that started the handoff, gets a session; a handoff is single-use. **Now:** API done (#29); no web client calls it.
- AC2: Expired, rejected and rate-limited handoffs each show a clear message and a retry button.
- AC3: `__Host-tilchi_sid` is HttpOnly, Secure, SameSite=Lax, Path=/, no Domain; nothing auth-related is stored in localStorage.

**J3 — Mini App login** (story 3)
- AC1: `POST /auth/miniapp` accepts `initData` only with a valid hash and `auth_date` ≤ 5 min old, and mints the same session as J2. **Now:** API exists; there is no Mini App client.

**J4 — Lesson day** (stories 25–38, 54)
1. The teacher creates a Lesson for a Group at an Asia/Tashkent time → learners are notified; reminders follow the Notification Catalog.
2. Teacher presses Start → status `live` → learners get a "Darsga kirish" link.
3. Learners join; the join records attendance.
4. Teacher presses End → the room closes, every participant is removed, status `ended`.
- AC1: The time picker reads input as Asia/Tashkent whatever the device time zone. **Now:** it uses the browser time zone — fails.
- AC2: A token is minted only for the Group's learners and its teacher (admins too if Q1 is approved), only while `live`, TTL ≤ 60 s; LiveKit keys never reach a client. **Now:** done; the code already lets admins in.
- AC3: After End nobody stays or rejoins (XAM-791). **Now:** End changes memory only.
- AC4: The meeting page publishes and renders camera and mic, with mute, leave and an audio-only fallback. **Now:** connect-only page.
- AC5: Cancel or reschedule notifies every Group learner on web and in the bot. **Now:** missing.
- AC6 **(Proposed)**: the teacher can mute or remove one participant without ending the Lesson (LiveKit server API).

**J5 — Test with speaking** (stories 43–50, 54)
1. The teacher assigns a published test to a Group with a deadline → learners are notified.
2. The learner answers once; speaking is recorded in the browser and uploaded through a presigned URL.
3. The teacher confirms choice answers, scores speaking, adds feedback → the learner is notified `graded`.
- AC1: A second attempt is refused; a submit after the deadline is refused (no late window **(Proposed)**; legacy allowed 3 days).
- AC2: Speaking upload ≤ 3 min and ≤ 10 MB per answer, `audio/webm` or `audio/mp4` **(Proposed)**; object keys hold no personal data.
- AC3: Status moves only `assigned → submitted → graded`, or `assigned → missed` when the deadline passes with no submission **(Proposed state)**. **Now:** the whole journey is missing.

**J6 — Lost device** (stories 7–9)
- AC1: Web logout ends only the current session; bot "revoke all" ends every session at once (Redis cache invalidated) and the bot confirms. **Now:** revoke-all is missing.

## Compliance & Privacy (Uzbekistan) — Proposed, confirm with local counsel

- **Data localization.** Law ZRU-547 "On personal data" (2019), Art. 27¹ (added 2021): personal data of Uzbek citizens processed over the internet must be collected, systematized and stored in databases on hardware physically in Uzbekistan and registered in the State Register of personal data bases ([lex.uz/docs/4396428](https://lex.uz/docs/4396428)). Postgres, Redis and backups on the UZ VPS comply.
- **C1 — speaking audio on R2 challenges a grilled decision.** A learner's recorded voice is personal data, and R2 has no Uzbekistan location. Default: **keep audio in-country** (S3-compatible storage on the VPS or at a UZ provider) behind the same presigned-URL API; use R2 only for non-personal assets. Owner decides.
- **Register the database** in the State Register before launch (owner task).
- **Consent.** The bot shows a short uz/ru/en privacy notice and a consent button before it collects registration fields; store the consent time and notice version. The consent explicitly covers cross-border processing: Telegram delivers bot messages from servers outside Uzbekistan, and AI helper requests go to a foreign model provider (ZRU-547 cross-border transfer rules, Art. 15 — confirm with counsel).
- **Minimize what leaves the country.** Bot DMs and admin-chat messages carry name, level and a link, never phone numbers. AI helper prompts carry lesson text only, never names or Telegram ids.
- **Minors (G7).** Under the Civil Code (Arts. 27–28) children under 14 act through their parents, and 14–18-year-olds need parental consent for most contracts, so a minor's data needs guardian consent (confirm with counsel). v1 has no parent role, so the default is: an admin adds a minor to a Group only after recording guardian consent (who gave it, when) on the User.
- **Retention (Proposed).** Speaking audio deleted 180 days after grading; unconverted registrations 12 months; audit log 1 year; sessions capped at 90 days; soft-deleted users purged within 30 days of a deletion request.
- **Rights.** A user can ask, through the bot or an admin, to see, correct or delete their data; the admin completes it within 30 days.

## Implementation Decisions

### Stack & topology
- **pnpm monorepo**: `apps/web` (TanStack Start), `apps/api` (NestJS + Drizzle), shared packages as needed.
- **Runtime**: Docker Compose on UZ VPS — nginx, Start, Nest, Postgres, Redis, LiveKit, coturn. Cloudflare DNS-only + **R2 only** (no Workers/Containers/D1 for app runtime). ADR 0010 supersedes CF-runtime ADRs for v1. R2 for learner audio is pending decision C1.
- **TLS**: Let's Encrypt on VPS. Firewall: 80/443 + LiveKit/TURN UDP; SSH not public.
- **Images**: build/push to ghcr.io **after merge to main**, tag = git SHA; deploy pulls that SHA.
- **Browser → API**: same origin; nginx routes `/api`, `/auth`, `/bot` to Nest. Start is **not** a BFF cookie proxy.
- **Paths**: `/` `/app` `/slide` `/canvas` `/app/meet` → Start; `/ws/canvas` → Nest (upgrade); `/rtc` → LiveKit signaling; `/ai/*` → Start (model via env).

### Auth & session
- Cookie: `__Host-tilchi_sid` HttpOnly Secure SameSite=Lax Path=/ (Nest sets). Optional CSRF: SameSite=Lax only (no double-submit token in v1).
- Postgres sessions = source of truth; Redis cache TTL 5m; logout/revoke invalidate cache.
- Deep-link pending handoff TTL 5m; session 30d sliding; multi-device; web logout = current only; bot revoke-all.
- Sliding means: authenticated responses renew the cookie for min(30 d, remaining absolute lifetime); activity extends idle expiry; all access ends 90 d after issue (absolute cap, as built). The per-Telegram rate limit must key on the server-verified Telegram id, not a client-supplied value (today it is client-supplied).
- Roles v1: `o‘quvchi` | `o‘qituvchi` | `admin`. **No parent/ota.** Learner self-serve in bot; teacher/admin allowlist.
- Admin UI inside `/app` role gates.
- Rate limit `/auth/start`: 5/min IP + 3/min telegram-related key; trust proxy / ignore client XFF (already fixed on main).

### Domain model
- Aggregates: **Group, Course, Lesson, Meeting**, plus Question bank.
- Lesson binds Group + scheduled time + Meeting; slide/canvas optional later attach.
- Lesson statuses: scheduled → live → ended | cancelled.
- Attendance = LiveKit join (manual mark deferred).
- 1:1 = Group with one learner.
- Course = public marketing catalog; Groups link to Courses; CTA → bot registration.
- Soft-delete User/Group/Course; PKs UUID v7; single-tenant.
- Group max 12; LiveKit room up to 12; size VPS for 1–3 concurrent rooms.

## Testing Decisions

### What good tests look like
- Assert **observable behavior** at the highest seam: HTTP/API contracts, auth cookie outcomes, domain status transitions, permission denials — not private Nest method names or React internals.
- Prefer TDD on Nest auth, Group/Lesson/Meeting services, and LiveKit token minting.
- UI: smoke and critical empty/error states later; do not invent coverage theater.
- PR gate (v1): **lint + typecheck + unit**. E2E not required on every PR.

### Primary seams (prefer these over new ones)
1. **Auth HTTP** — `/auth/start`, confirm, Mini App initData, logout, rate limits, cookie attributes.
2. **Session store** — Postgres truth + Redis cache invalidation on revoke.
3. **Group/Lesson/Meeting API** — create, membership (admin-only add), status transitions, Start/End.
4. **LiveKit mint** — only Group members + teacher; no API keys to client; End teardown (when XAM-791 lands).
5. **Canvas WS** — auth’d upgrade path; pub/sub fanout (integration/contract level).
6. **Audio presign** (R2 or in-country store, per C1) — speaking upload URL issuance and ACL assumptions.
7. **Notification fanout** — event → web + bot adapters (unit with fakes).
8. **Compose/config** — `${VAR:?}` fail-fast; migrate-before-up documented/scripted.
9. **Persistence (Proposed)** — repositories against a real Postgres in CI, plus migrations applied to an empty database.
10. **Bot entry points (Proposed)** — every `/start` form routes correctly: handoff id, `<segment>_<level>`, bare.

**Release gate (Proposed):** the acceptance criteria of journeys J1–J6 pass on a staging stack before deploy unhold.

### Prior art
- Existing unit coverage on auth confirm path from #29; Nest DI boot tests from #26/#28 era; demo seed fixtures from #30. Extend those patterns rather than new frameworks.
